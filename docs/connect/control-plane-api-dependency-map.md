Required operation shape for each lifecycle resource:

- `GET base` and `GET base/:id/versions/:version` for bounded list/detail reads;
- `POST base` creates version 1 in `DRAFT` with an idempotency key;
- `PATCH base/:id/versions/:version` updates only the current draft and requires `expectedVersion`;
- `POST .../submit-review`, `POST .../publish`, `POST .../retire`, and `POST .../rollback` are explicit commands, not status field patches;
- every command requires reason, expected version, idempotency key, actor and before/after audit evidence;
- preview and semantic diff are read endpoints over immutable versions;
- `PUBLISH`, `RETIRE` and `ROLLBACK` require `settings.manage` plus step-up at minimum. Any finer permission or separation-of-duties key must be defined by the backend owner, not invented here;
- runtime consumers resolve only published versions; secrets, provider credentials, hidden reasoning and raw prompts are excluded from every response.

## Plans dependency

Agent 2 canonically records Plans as `BLOCKED`: no versioned Plans application-service contract exists. The current Prisma split uses `Plan.name` plus `PlanVersion` fields and statuses `DRAFT`, `UNDER_REVIEW`, `ACTIVE`, `SUSPENDED`, `RETIRED`, `ARCHIVED`. The approved Control Plane contract requires `code`, features, benefits, pricing/currency, commercial text, public/Koral visibility, recommendation, display order, effective range and version, with `DRAFT`, `REVIEW`, `PUBLISHED`, `RETIRED`.

There is no safe one-to-one mapping for status, identity, visibility, recommendation, ordering or structured commercial content. This consumer does not implement a backend, migration or translation.

Blocked screens/consumers:

- `/admin/planes`: list, editor, preview, diff, review and publication;
- public plan/benefit experiences that must read the single published source instead of static catalog content;
- Koral Knowledge, Recommendations, Tools and conversation responses that mention plan eligibility, price, benefits or terms;
- analytics that attribute conversations, recommendations or conversions to a published plan version.

## System versus Koral

- Koral contains functional/business configuration: model profiles, agents, tools, knowledge, recommendation policies and business automations.
- Sistema contains OpenRouter, Meta, WhatsApp and other provider connection/health/usage plus technical diagnostics.
- Koral dashboards must not infer or duplicate provider health. Sistema must not expose prompts, policies, business configuration or secrets.
