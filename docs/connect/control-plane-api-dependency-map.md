## Koral and Communications Admin requirements

The paths below remain requirements, not implemented endpoints. Every lifecycle resource needs bounded `READ`, `CREATE_DRAFT`, `UPDATE_DRAFT`, `SUBMIT_REVIEW`, `PUBLISH`, `RETIRE` and `ROLLBACK` operations unless the canonical lifecycle explicitly adds another state or makes an operation inapplicable.

| Analytics/evaluations                   | `/api/v1/admin/koral/analytics` and `/api/v1/admin/koral/evaluations` | Agent 2 eval/usage contracts                                     | `BACKEND_RUNTIME_MISSING`; immutable results are read-only and not rollback targets.                        |
| Communication templates                 | `/api/v1/admin/communications/templates`                              | Agent 3 Template/Version and preview contract                    | `BACKEND_RUNTIME_MISSING`; canonical preview and `DRAFT -> REVIEW -> PUBLISHED -> RETIRED/ROLLED_BACK`.     |
| Communication automation/history/config | `/api/v1/admin/communications/{automations,history,configuration}`    | Agent 3 automation/communications models                         | `BACKEND_RUNTIME_MISSING`; never expose rendered bodies, recipients or provider details in audit responses. |

Required operation shape: list/detail reads; draft creation with idempotency key; draft-only patch with expected version; explicit submit-review/publish/retire/rollback commands; immutable version preview and semantic diff. Mutation commands require reason, expected version, idempotency key, RBAC and before/after audit. Publish, retire and rollback require step-up at minimum. Runtime consumers resolve published versions only. Secrets, credentials, hidden reasoning and raw prompts are excluded from responses.

## Plans dependency

Agent 2's canonical design gate confirms `MIGRATION_REQUIRED=YES` but deliberately implements no service, route or migration. Decisions remain open for `code` backfill, canonical name, feature/benefit schemas, price/currency vocabulary, lifecycle mapping, visibility and effective-date defaults. Therefore `/admin/planes`, public plan consumers, Koral plan-aware knowledge/tools/recommendations and plan-attributed analytics remain `BLOCKED_BY_PLANS`.

The future design keeps one stable PostgreSQL Plan identity and immutable versions, with one published-version pointer consumed by Admin, public pages, Koral, CRM and Contracts. Master/Firebird remains only an optional projection. This branch implements no mapping or backend.

## System versus Koral

- Koral contains functional/business configuration: model profiles, agents, tools, knowledge, recommendation policies and business automations.
- Sistema contains OpenRouter, Meta, WhatsApp and other provider connection/health/usage plus technical diagnostics.
- Koral dashboards do not infer or duplicate provider health. Sistema does not expose prompts, policies, business configuration or secrets.
